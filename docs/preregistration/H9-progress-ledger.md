# H9 (dropped): a code-generated progress ledger for the planner

Status: **dropped by the author's decision of 2026-10-13, before any H9 task existed.** It is kept only as
a design record. It is not registered, not in the Holm family, and nothing is measured for it.

## Background

In the held-out run of 2026-10-06, 138 of 242 executed steps were rejected repeats of an identical action
(`docs/analysis/terminal-state-diagnosis.md`). Related work (wording verified in
`docs/preregistration/CITATIONS.md`):
- **Explicit state tracking** cut average ALFWorld steps from 31.49 to 19.11 with gpt-3.5. With
  Qwen2.5-7B, ALFWorld rose from 0.10 to 0.46 but WebShop fell from 0.19 to 0.12 (StateAct, Rozanov and
  Rei, REALM 2025 workshop at ACL).
- **Programmatic failure signals** worked better than self-diagnosis (Dixit et al., arXiv:2605.29463,
  ICML 2026 workshop).
- **Fingerprinting** tool calls as a hash of name and arguments, triggered at 3 repeats, is a published
  design but not an evaluated result (Bui, arXiv:2603.05344, preprint).

## The treatment (not yet implemented)

- **Loop guard** (`ARIES_LOOP_GUARD`, on in **both** arms):
  - Each step gets a fingerprint: a hash of the capability, its normalised arguments, and a hash of the
    relevant state the verifier observed.
  - An exact repeat of a step that already succeeded, with unchanged state, is blocked. It returns
    `already_done` with the verified state.
  - After 2 blocks in one goal, the goal ends and the completion contract decides.
- **Ledger** (`ARIES_PROGRESS_LEDGER`, the treatment): generated by code, never by the model. It holds:
  - the goal;
  - completed steps, with fingerprint and verifier verdict;
  - current verified facts;
  - remaining contract items;
  - fingerprints that already failed.

  It replaces the raw history at the top of each planner call. The planner schema gets a `candidates`
  field, and more than one candidate goes to the H4b path.

## Hypothesis

**H9.** With the ledger on, multi-step episodes contain fewer redundant steps, and goal success is
non-inferior within 5 percentage points.

## Materials

At least 60 multi-step tasks, written by another person who has not seen the code. Each has an oracle
for success and a definition of what counts as a redundant step. The oracles are validated against a
do-nothing run before measurement.

## Procedure

- Ledger on vs off, loop guard on in both arms.
- 2 models (qwen2.5:7b, llama3.1:8b) × 3 seeds, paired by task, alternated.
- Isolated databases. The live ARIES is stopped and screen blanking is off.
- The model digests and Ollama version are recorded.

## Primary outcome and test (for the Holm correction)

The number of redundant steps per episode, paired by task and seed, with qwen2.5:7b. Tested with a
one-sided Wilcoxon signed-rank test (ledger lower), at α = 0.05 before Holm.

## Non-inferiority guard

Goal success, ledger on minus off. Met if the one-sided 95% Newcombe bound of the paired difference is
above −5 points.

## Secondary

- the same measures for llama3.1:8b;
- steps per episode;
- loop-guard blocks per episode;
- terminal states.

## Stated in advance

- The loop guard alone (on in both arms) already removes exact repeats. H9 measures only what the
  ledger adds on top.
- StateAct got worse with Qwen2.5-7B on one benchmark, so a null or negative result is plausible.
- **This hypothesis is the first to drop if time is short.** If it is dropped, the Holm family shrinks
  to the remaining confirmatory tests, and that is reported.
