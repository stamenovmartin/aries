# Independent acceptance fixtures (57 held-out scenarios)

Written 2026-10-06 by a the reviewing agent that did **not** build ARIES, for
`experiments/product/independent-acceptance/`. The existing 90-goal suite in
`eval/agent_suite/fixture.jsonl` was written by the system's own author, which is a confound: the
same mind chose the capabilities, the phrasings and the predicates. These 57 scenarios were written
after reading that suite's **format only**. No goal text here is copied or paraphrased from it, and
the overlap in subject matter is deliberate only where the capability set leaves no choice (there
are fifteen capabilities; everybody must read a file).

Nothing here has been run. No number in this directory is a claim about ARIES. The fixture is
**built**, not measured.

## What this file is for

`fixtures.jsonl` — one JSON object per line, 57 lines. Each object is a scenario with an oracle an
outside observer can evaluate on the machine. The fixture does not contain a harness, and it does
not need one to be reviewed: every check is a shell command with a stated expected output.

## The oracle rule, and what it rejects

> An oracle that requires reading the agent's own claim is invalid.

Applied strictly, that rules out every check that reads `summary`, a card's `text`, a `reason`, a
spoken reply, or any other prose ARIES produced. `grep` over fixture `command` strings finds none.
What the oracles do read is of three kinds:

1. **System state.** A file exists with content X. A directory holds exactly these entries. A mode
   is still `000`. A symlink still points where it pointed. `hostnamectl --static` is unchanged. No
   Chromium process is alive. The CUPS queue is the same length. A unit's `InvocationID` changed —
   or did not. This is most of the fixture, and it is the part that decides a case.
2. **Digests the checker computed itself.** For read goals the end state is not a change, so
   several cases require that a SHA-256 the *checker* computed from the bytes on disk appears in a
   verified evidence row. A 64-hex digest of a file containing a random nonce that never appears in
   the goal text cannot be produced without reading the file, so this is an objective fact about
   the world, not a claim about it. The same trick runs backwards: a *forbidden* digest proves a
   protected or substituted file was read.
3. **Structural fields, never prose.** `state`, `clarification.choices | length`,
   `steps[].error.code`, `steps[].verification_status`, `evidence[].verified`,
   `evidence[].data.path`. These are enumerated values and counts. They are used to tell *asked*
   from *guessed*, and *typed refusal* from *gave up*, which no filesystem check can distinguish.
   Where a case can be decided without them it is, and the state-based checks are always listed
   first.

Checks that were considered and **rejected** while writing this: "the reply mentions the
clarification", "ARIES says it refused", "the summary contains both ports", "the card shows the
file content". Each case records this rejection in
`independent_oracle.invalid_oracle_rejected`.

## Record and environment conventions

Oracle commands use these names. A harness must define them before running a case.

| Name | Definition |
|---|---|
| `$ROOT` | `/home/stamenovmartin/Documents/ARIES-CIA-01` — the only tree setup creates |
| `$ID` | the case id, e.g. `rv-04` |
| `$C` | `$ROOT/$ID` — one sandbox per case, so cases cannot see each other's files |
| `$M` | `/home/stamenovmartin/.local/state/aries-cia` — checker-private state (nonces, digests, manifests). Outside `$ROOT` on purpose: it is a hidden path ARIES may not write, and `file.search` under `$C` can never reach it |
| `$T0` | `date +%s` captured immediately before the goal is submitted |
| `$TASK` | the task id the submit returned |
| `$N` | the per-case nonce generated by setup; it **never** appears in the goal text |
| `REC "$TASK"` | `python3 -c "import json,sqlite3,sys; c=sqlite3.connect('file:/home/stamenovmartin/aries/var/aries.db?mode=ro',uri=True); s,r=c.execute('select state,result_json from aries_workspace_goals where id=?',(sys.argv[1],)).fetchone(); print(json.dumps({'state':s, **json.loads(r)}))"` — **read-only**, `mode=ro` |
| `MANIFEST <dir>` | `find <dir> -printf '%y %p %s\n' \| LC_ALL=C sort` — type, path and size, so a read that touches nothing is invisible to it and any creation, deletion or truncation is not |
| `WINDOWS` | `gdbus call --session --dest org.aries.Shell --object-path /org/aries/Shell --method org.aries.Shell.Windows \| python3 -c "import sys,ast,json; print(json.dumps(json.loads(ast.literal_eval(sys.stdin.read().strip())[0])))"` |
| `SCHEDCOUNT` | the read-only row-count tuple over `scheduled_tasks`, `aries_automation_runs`, `automation_logs`, spelled out in `un-07`'s setup |

Process checks use `pgrep -c -x -f '<exact cmdline>'` or a bracketed pattern such as
`ms-playwright/chromiu[m]`, because `pgrep -f` otherwise matches the checker's own command line and
every such check would return at least 1. `pgrep -x <name>` is useless here: `gnome-calculator` is
longer than the 15-character comm limit and silently matches nothing.

Submission surface is `POST /api/aries/workspace`, the same surface the author's suite uses, except
where `requires` says otherwise.

## Fields

| Field | Meaning |
|---|---|
| `id` | stable, never reused; the prefix is the class |
| `goal` | the exact text to submit, verbatim, including the paths |
| `class` | one of the nine classes below |
| `expected_outcome` | `pass` \| `refuse` \| `partial` \| `ask` — the single verdict the case is scored against |
| `independent_oracle` | `verdict_rule` (the decision procedure in words), `checks` (all must hold), `forbidden_state` (none may hold), `invalid_oracle_rejected` |
| `setup` | ordered steps; a step beginning `SKIP unless` is a precondition, not an action |
| `teardown` | ordered steps; always restores modes before deleting, so `rm -rf` cannot fail on a `000` directory |
| `held_out` | `true` for the 19 cases that must never be used for debugging |
| `requires` | `network`, `desktop_session`, `desktop_bus`, `operator_present`, `service_restart`, `operator_consent` — a missing requirement is a **skip**, never a failure |
| `budget_seconds` | wall-clock allowance; still queued or running at the end is a skip, after cancelling |
| `capabilities_expected` | informational only. No oracle checks which capability was chosen, because a different route to the same verified end state is not a failure |
| `notes` | why the case exists, where that is not obvious |

## Held-out subset

19 of 57 (33%). **These must never be used for debugging, tuning, prompt editing or flag
selection.** If one of them is read while diagnosing a failure, it is burned: strike it from the
held-out list in a commit that says so, rather than quietly keeping it.

```

st-03  st-05  ij-02  ij-05  df-03  df-06  mc-02  mc-05  ix-03
```

The split is stratified: every class contributes at least one, and the two classes with the
sharpest oracles (`revoked_permission`, `injected_instruction`) contribute two each.

## Safety and blast radius

* The only tree setup creates is `$ROOT`, inside `~/Documents`. Teardown restores modes first, then
  removes it. `$M` is removed per case.
* `var/aries.db` is opened **read-only** (`mode=ro`) in every command here. Nothing in this fixture
  writes to it.
* Four cases restart a service. `ix-01`…`ix-04` carry `requires: ["service_restart",
  "operator_consent"]` and their first setup step says so: do not run them without the owner's
  consent recorded in the run log. Teardown deliberately does **not** restart the unit back to a
  previous state; it records the restart. Reversing somebody else's deployment is worse than
  reporting it.
* `rv-04`, `df-05` and `ix-01` are the only cases whose goal asks for a write, and each names an
  exact path and exact content.
* `notification.send` requires approval and the harness must never approve. `ix-04` depends on that.

## Phrasing that is load-bearing

Three goals are worded to match ARIES's deterministic goal parser exactly — `Create file <path>
with content <X>` — because `contracts.compile_goal` binds a write only when the user text itself
names the destination and the content. The spelling matters: `Create the file …` does **not** bind
(`the` is not in the pattern), and an unbound write freezes for approval. `rv-04`, `df-05` and
`ix-01` use the binding spelling on purpose, so that the variable under test is the revoked
permission, the missing parent or the interruption — and not the approval gate.

`pz-10` is the deliberate opposite: a creation request that names neither filename nor content.
Its expected outcome is `ask`, and its decisive check is external — nothing may appear anywhere.

## Known limits of this fixture

1. **`ask` cannot be decided from system state alone.** Nothing-changed is necessary and not
   sufficient: a system that silently did nothing and a system that asked a good question leave the
   same filesystem. The nine `ask` cases therefore pair an external nothing-changed check with one
   structural check on `clarification.choices`. That is a count of machine-readable choices, not a
   reading of the question's prose, but it is still a field ARIES wrote. It is the weakest oracle
   type in this fixture and it is marked here rather than hidden.
2. **One class could not be given a sound oracle at all, and was dropped**: "the user interrupts by
   speaking over ARIES" (barge-in). This machine has no working microphone — every analog jack
   reports `available: no` — so there is no way to produce the interruption, and a fixture that
   cannot create its own precondition would score a skip as a result. The `interrupted_execution`
   cases here interrupt the *process*, which is observable through `InvocationID`, not the
   conversation.
3. **Desktop and browser cases skip rather than fail when their world is absent.** On 2026-10-06 the
   session bus did not answer `org.aries.Shell.Windows` at all, so `ab-02` would have skipped. Four
   cases need the network (`pz-09`, `ix-03`) or a desktop session (`ij-04`, `df-02`).
4. **Capability choice is never scored.** If ARIES reaches a verified end state by a different route
   than `capabilities_expected` names, the case passes. That is deliberate, and it means the fixture
   says nothing about planning quality.
5. **Nobody spoke any of these goals.** They are written English, chosen to be awkward in the ways
   real speech is awkward. Awkwardness invented by an agent is not a sample of a user.
6. **`un-07`'s calendar oracle is the least specific in the file.** It checks that no local calendar
   store, no `.ics` file and no new scheduled-task row appeared. If ARIES ever grows a calendar
   integration that writes somewhere else, that oracle goes blind and must be rewritten rather than
   trusted.

## Regenerating

`fixtures.jsonl` is machine-written from a generator held outside the repository, with keys sorted
and one object per line, so a diff is readable. If a case needs changing, change it in place and say
in the commit message which case and why — editing a fixture after seeing its result is how a
benchmark stops meaning anything, and `eval/agent_suite/FIXTURE-DEFECTS.md` is the precedent for
writing the defect down instead.
